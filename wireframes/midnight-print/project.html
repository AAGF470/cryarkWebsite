Simply Simple Foliage

A node-based foliage creator for game development, animation, and digital art — without a subscription, and without fighting an aging interface to do it.

In dev Blender Python Foliage Product offering

You author a tree as a set of connected nodes, shaping how it grows through an intuitive field-based system, then let Blender handle the heavy lifting of mesh generation, UVs, normals, and armatures behind the scenes. The result is clean, animation-ready foliage you can drop straight into your engine.

SSF is built for indie developers who need custom trees, vines, and plants but don't want to pay forever for software they never own. It does one thing and does it well: get you from idea to a game-ready tree, fast.

№ 2 — StrategyThe core bet

Most tools in this space — SpeedTree, Tree It, various Blender add-ons — build their own everything: renderer, mesh pipeline, viewport. That works at first and decays over time. Tree It is the cautionary example: impressive in 2012, built on DirectX 9, and now actively breaking down because the foundation underneath it moved on.

Own the logic, not the stack. The renderer, mesh construction, UV math, and armature generation are delegated to Blender. What SSF owns is what differentiates it: the procedural model, the editing system, the data architecture, and the workflow. Those age well. A hand-rolled renderer does not.

SSF never embeds Blender or modifies it. It runs Blender as an external process, hands it data, and lets it do the heavy lifting — a pattern validated in DERG, which spawns headless Blender subprocesses to render synthetic training footage.

№ 3 — SystemsThe growth field

A tree's shape comes from a vector field — a 3D grid of directions that nodes follow as they grow. A node steps forward, samples the field at its location, bends according to what the field says, and steps again.

The design choice worth noting: the tree never holds a reference to the field. Nodes sample it by position during generation, then forget it. The connection is emergent, not wired — and emergent connections can't fall out of sync.

№ 4 — SystemsContainers: localizing change

A tree isn't a flat pile of nodes. It's composed of containers — typed objects (trunk, branch, branchlet, root) that each hold a line of nodes. When a user hand-edits one branch, that edit is bounded inside its container; a touched container is flagged so the system preserves it rather than regenerating over the user's work — directly addressing the most common SpeedTree complaint.

Containers connect by reference, not stored position: a branch records "I attach to exit point 2 of trunk 5" and resolves that to a position only when it regenerates. Compute on demand rather than cache — nothing to keep in sync. Regeneration order isn't designed; it's forced by the data itself.

№ 5 — PhilosophyDeliberate limitations

When a hand-edited branch's parent later moves, SSF doesn't guess how the branch should re-grow. It freezes it as custom geometry and rigidly moves it with its parent. The user keeps their work, exactly as they made it.

A predictable limitation beats a fragile feature. A feature that's right most of the time and silently wrong the rest is worse than a limitation that's always honest.

The throughline: push complexity into the data model so it doesn't live in fragile coordinating code. Connections are computed, not cached. Order falls out of dependencies. Failure modes are designed out structurally.
